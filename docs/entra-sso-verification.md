# EntraテナントでのSSO確認手順

AIRA Nexusの基盤①を対象に、実際のMicrosoft Entraテナントでログイン・APIアクセス・ログアウト・ユーザー間分離を確認する手順です。
開発者とテナント管理者が実施し、観測した結果を合否表へ記録します。この手順書を作成した時点では、実テナントでの確認は未実施です。

更新: 2026-11-12。対象実装: `src/client/auth.ts`、`src/client/api.ts`、`src/server/identity.ts`。
要件の正本は [identity](../.sdd/specs/identity.md) と [workbench](../.sdd/specs/workbench.md)、起動方法は [README](../README.md) を参照してください。

## 1. 確認範囲と合格条件

基本確認SSO-01〜SSO-07がすべて成功した場合に、「当該環境で基本SSO確認済み」とします。
割り当て制限・トークン更新・再認証はSSO-08〜SSO-10で別に判定し、未実施を合格扱いしません。
本手順の成功は、本番公開の承認、全APIの認可試験、負荷・復旧・Kubernetes配備の確認を意味しません。

| 区分         | 確認すること                                                   | 確認しないこと                        |
| ------------ | -------------------------------------------------------------- | ------------------------------------- |
| 認証         | 実EntraアカウントによるPKCEのポップアップ認証と委任APIアクセス | パスワードの取得、認証のバイパス      |
| セッション   | 同じタブでの再読込、明示的なサインアウト、再サインイン         | 全端末・全アプリの一括サインアウト    |
| プロジェクト | 本人の作成・改名・永続化と、別ユーザーの一覧からの分離         | 共有・削除、手動での全API攻撃パターン |
| 後続機能     | 未提供の操作が無効であること                                   | AI応答・ファイル操作・Python/R実行    |

## 2. 必要な権限・環境・試験アカウント

Entraのアプリ登録、APIの委任アクセス許可、同意、エンタープライズアプリへの割り当てを扱える担当者を用意します。必要な権限は組織の管理ポリシーに従います。
担当者は、アプリ登録画面の操作、`.env` の編集、シェルでの起動方法を理解していることを前提とします。

- Node.js 24、npm、Docker Compose、PostgreSQL 17を利用できる検証環境。
- Microsoft公開クラウドの単一テナント。政府機関向けクラウド等の別authorityは現行実装の対象外。
- 同じテナントに属し、利用を許可した試験アカウントA・B。
- ポップアップを許可できるブラウザーと、A・Bで分離したブラウザープロファイル。
- ブラウザーの開発者ツールで、HTTPの通信先・パス・ステータスを確認できること。
- ブラウザーからEntraの認証エンドポイント、APIサーバーから `login.microsoftonline.com` の署名鍵エンドポイントへHTTPSで接続できること。

同じブラウザーの複数のInPrivate／シークレットウィンドウは、Microsoft側のセッションを共有する場合があります。A・Bの分離確認には別プロファイルを使用してください。
既存の本番アプリや組織全体のConditional Accessを変更せず、可能なら専用の検証用アプリ登録とDBを使用します。

**証跡の注意**: パスワード、Authorizationヘッダー、JWT、認可コード、Cookie、MSALのストレージ内容、DB接続URLを保存・共有しないでください。
HARの一括出力や「Copy as cURL」は資格情報を含むため使用しません。JWTを外部のデコードサイトへ貼り付けないでください。
記録上の利用者はA・Bなどのラベルとし、メールアドレス、表示名、個人のobject IDが写る画像やログはGitに保存しません。

## 3. EntraのAPI・SPA登録を確認する

### 3.1 API用アプリ

1. [Microsoft Entra管理センター](https://entra.microsoft.com/) で、対象テナントに切り替えます。
2. 「アプリの登録」で、作成済みのAPI用アプリ `aira-nexus` を開きます。新規作成は不要です。
3. サポートするアカウントの種類を「この組織ディレクトリのみ」に設定します。
4. 「概要」のディレクトリIDを `ENTRA_TENANT_ID`、`aira-nexus` のアプリケーションIDを `ENTRA_API_CLIENT_ID` の設定用に控えます。
5. 「マニフェスト」で `api.requestedAccessTokenVersion` を `2` に設定します。既存のマニフェスト全体を置換しないでください。
6. 「APIの公開」でアプリケーションID URIを `api://<APIのアプリケーションID>` に設定します。
7. 名前が `access_as_user` のスコープを有効な状態で追加します。同意を行える主体と表示文言は管理者が組織の方針に従って設定します。

スコープ追加画面の各項目は、以下のように設定します。社内利用を想定し、管理者が事前に同意する設定例です。組織の規程がある場合は、そちらを優先してください。

| 項目                             | 設定値                                                                                                                                         |
| -------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| 同意できるユーザーはだれですか？ | **管理者のみ**                                                                                                                                 |
| 管理者の同意表示名               | サインインしたユーザーとしてAIRA Nexusを利用する                                                                                               |
| 管理者の同意説明                 | アプリがサインインしたユーザーに代わってAIRA Nexus APIへアクセスし、そのユーザー本人のプロジェクトを一覧表示・作成・改名することを許可します。 |
| ユーザーの同意表示名             | 空欄。「管理者のみ」では使用しません。                                                                                                         |
| ユーザーの同意の説明             | 空欄。「管理者のみ」では使用しません。                                                                                                         |
| 状態                             | **有効**                                                                                                                                       |

入力後に「スコープの追加」をクリックします。これだけでは管理者同意は完了しません。3.2の手順7で、SPAに追加した委任アクセス許可に対して管理者同意を付与してください。
「管理者のみ」は同意を行える主体の制限であり、アプリの利用者を管理者だけに限定する設定ではありません。ユーザーの利用可否は3.3の割り当て等で管理します。
「管理者とユーザー」を選ぶ運用の場合は、ユーザーの同意表示名と説明も入力します。例はそれぞれ「自分のAIRA Nexusプロジェクトを利用する」と「このアプリがあなたに代わってAIRA Nexus APIへアクセスし、あなたのプロジェクトを一覧表示・作成・改名することを許可します。」です。ユーザー自身が同意できるかどうかは、テナントのユーザー同意ポリシーにも依存します。

確認点: 完全な委任スコープが `api://<APIのアプリケーションID>/access_as_user` になっていること。
API用アプリには、今回の対話ログイン用リダイレクトURIやclient secretは不要です。アプリケーション権限や `roles` だけでは、このAPIの要求を満たしません。

### 3.2 SPA用アプリ

SPAはSingle-Page Applicationの略で、ここではブラウザーで動くAIRA NexusのReact画面を指します。
この画面がEntraへサインインを要求し、取得したアクセストークンを使ってAPIを呼び出します。3.1のAPI用アプリとは役割が異なるため、別のアプリ登録を使用します。

| 用途  | 登録名                                     | 役割                                                      | `.env` に設定するID   |
| ----- | ------------------------------------------ | --------------------------------------------------------- | --------------------- |
| API用 | `aira-nexus`（作成済み）                   | トークンを検証し、本人のプロジェクトを提供する            | `ENTRA_API_CLIENT_ID` |
| SPA用 | `aira-nexus-spa`（以下で使用する名前の例） | ブラウザーからサインインし、APIへのアクセス許可を要求する | `ENTRA_SPA_CLIENT_ID` |

`aira-nexus-spa` は推奨例であり、作成済みという意味ではありません。別の名前でも構いません。既存の専用SPA登録がある場合は、それを開いて各設定を確認し、重複して作成しないでください。

#### 手順1：SPA用のアプリ登録を作る

1. Microsoft Entra管理センターで、`aira-nexus` を作成したテナントに切り替えます。
2. 「Entra ID」→「アプリの登録」を開きます。
3. 「新規登録」をクリックします。
4. 下表の値を入力します。
5. 「登録」をクリックします。

| 登録画面の項目                     | 入力・選択する値                                                     |
| ---------------------------------- | -------------------------------------------------------------------- |
| 名前                               | 例: `aira-nexus-spa`。API用の `aira-nexus` と区別できる名前          |
| サポートされているアカウントの種類 | **この組織ディレクトリのみに含まれるアカウント**（シングルテナント） |
| リダイレクトURI（省略可能）        | この時点では空欄。手順4でSPAプラットフォームとして登録する           |

登録後にSPA用アプリの「概要」が表示されることを確認します。以降の操作は、API用の `aira-nexus` ではなく、このSPA用アプリを開いた状態で行います。

#### 手順2：SPAのIDとテナントIDを控える

SPA用アプリの「概要」で、以下の値を控えます。4節で `.env` を設定するときに使用します。

| 画面の項目                         | 用途                                               |
| ---------------------------------- | -------------------------------------------------- |
| アプリケーション（クライアント）ID | `ENTRA_SPA_CLIENT_ID` に設定するUUID               |
| ディレクトリ（テナント）ID         | `ENTRA_TENANT_ID` に設定するUUID。3.1のAPIと同じ値 |
| オブジェクトID                     | 今回の `.env` 設定には使用しない                   |

**API用とSPA用のクライアントIDは異なります。** 表示名の `aira-nexus-spa` や、API用のクライアントIDを `ENTRA_SPA_CLIENT_ID` に入れないでください。

#### 手順3：画面を開くURLと認証後の戻り先を決める

リダイレクトURIは、Entraでの認証処理後にポップアップを戻す先です。任意のURLではなく、AIRA Nexusが要求する `/auth-redirect.html` を登録します。
初回のローカル開発では、下表のVite開発サーバーの行を使用します。

| 実行モード                  | `PUBLIC_ORIGIN`         | SPAに登録するリダイレクトURI               |
| --------------------------- | ----------------------- | ------------------------------------------ |
| Vite開発サーバー            | `http://localhost:5173` | `http://localhost:5173/auth-redirect.html` |
| ビルド済み画面をAPIから配信 | `http://localhost:3000` | `http://localhost:3000/auth-redirect.html` |
| HTTPS検証環境               | 実際のHTTPSオリジン     | 同じオリジンの `/auth-redirect.html`       |

`PUBLIC_ORIGIN` は画面のスキーム・ホスト名・ポートまでの値で、パスや末尾の `/` を付けません。一方、リダイレクトURIには `/auth-redirect.html` まで含めます。
ブラウザーで開くURLと、この表の設定を一致させてください。`localhost` と `127.0.0.1` を途中で混在させません。
Microsoft EntraはlocalhostのURI照合でポートを無視するため、5173と3000のようにポートだけ異なるURIを同じSPAへ重複登録しません。
実行モードを切り替える場合は、専用の検証用SPAで登録URIと `PUBLIC_ORIGIN` を使用するモードへ変更します。共有アプリのURIを無断で削除しないでください。
根拠はMicrosoftの [localhostの例外](https://learn.microsoft.com/en-us/entra/identity-platform/reply-url#localhost-exceptions) を参照してください。
リモートLinuxをWindowsから確認する場合は、[SSHトンネルの手順](ssh-tunnel-verification.md) を使用します。この経路ではビルド済み画面もlocalhost:5173で開きます。

#### 手順4：SPAプラットフォームにリダイレクトURIを登録する

1. SPA用アプリの「管理」→「認証」を開きます。
2. 「リダイレクトURIの構成」タブで「リダイレクトURIの追加」をクリックします。
3. プラットフォームの選択で **シングルページアプリケーション（SPA）** を選びます。
4. 下表に従い、画面に表示されている項目を設定します。
5. 「構成」をクリックします。

専用の検証用SPA登録では、次のように設定します。

| 画面の項目                                             | 設定値                                                                       | 説明                                                                                                  |
| ------------------------------------------------------ | ---------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| リダイレクトURI／リダイレクトURL                       | 手順3で選んだURI。開発モードの例: `http://localhost:5173/auth-redirect.html` | `/auth-redirect.html` まで入力します。ビルド済み画面やHTTPS環境では、手順3の対応するURIを使用します。 |
| フロントチャネルのログアウトURL                        | **空欄**                                                                     | ポップアップの戻り先ではありません。ここに `/auth-redirect.html` や `PUBLIC_ORIGIN` を入力しません。  |
| 暗黙的な許可およびハイブリッドフロー：アクセストークン | **チェックを入れない（オフ）**                                               | API用のアクセストークンは、認可コード＋PKCE方式で取得します。                                         |
| 暗黙的な許可およびハイブリッドフロー：IDトークン       | **チェックを入れない（オフ）**                                               | サインインに必要なIDトークンも、認可コード＋PKCE方式で取得します。                                    |

項目の表示位置は画面構成によって異なります。追加画面にログアウトURLやチェック項目が表示されない場合は、URIを構成した後に「認証」の「設定」タブなどで確認してください。変更を行った場合は「保存」をクリックします。

アクセストークンとIDトークンのチェックは、暗黙的な許可・ハイブリッドフローを有効にするための項目です。両方をオフにしても、認可コード＋PKCEによるサインインとトークン取得は行われます。
ログアウトのポップアップは、実装が指定する登録済みリダイレクトURIへ戻ります。フロントチャネルのログアウトURLとは別の設定です。認証方式の理由は手順5を参照してください。

画面によっては、上記の項番2にある追加操作が「プラットフォームを追加」と表示されます。既存のSPA設定を編集する場合も、そのSPAのURI一覧へ追加し、変更を保存してください。
完了後、「シングルページアプリケーション」の設定に対象URIが表示されていることを確認します。**「Web」への登録ではありません。**
同じURIを誤って「Web」に登録した場合は、専用の検証用アプリであることを確認してSPA側へ登録し直します。共有アプリの既存URIを無断で削除しないでください。

#### 手順5：不要な認証方式やsecretを追加しない

現行実装はMSAL Browserを使った認可コード＋PKCE方式です。PKCEは、ブラウザーが開始した認証要求とコード交換を結び付ける仕組みです。
ブラウザーには秘密情報を安全に保管できないため、SPA用アプリにはclient secretを作成・設定しません。

| 項目                                                       | 今回の設定                                                             |
| ---------------------------------------------------------- | ---------------------------------------------------------------------- |
| 暗黙的な許可／Implicit grantのアクセストークン・IDトークン | 専用の新規登録ではチェックを入れない。認可コード＋PKCEで取得する       |
| 証明書とシークレット                                       | SPAのためにclient secretを追加しない                                   |
| フロントチャネルログアウトURL                              | 専用の新規登録では空欄。今回のポップアップの戻り先を設定する欄ではない |

**ログインとログアウトのポップアップは、どちらも登録済みの `/auth-redirect.html` に戻ります。** サインアウト後のメイン画面は `PUBLIC_ORIGIN` に移動します。
これらのURIは実装が指定します。ログアウトのために別のclient secretやImplicit grantを有効化する必要はありません。

#### 手順6：SPAからAPIを呼び出す委任アクセス許可を追加する

委任アクセス許可は、アプリがサインインしたユーザーに代わってAPIを利用するための権限です。
APIがスコープを「公開する」3.1の設定と、SPAがそのスコープの「利用を要求する」この設定は別の操作です。

1. SPA用アプリの「APIのアクセス許可」を開きます。
2. 「アクセス許可の追加」をクリックします。
3. 「自分のAPI」または「所属する組織で使用しているAPI」を開きます。
4. 名前 `aira-nexus` または3.1で控えたAPIのアプリケーションIDで検索します。
5. API用アプリの `aira-nexus` を選びます。
6. **委任されたアクセス許可** を選びます。
7. `access_as_user` にチェックを入れます。
8. 「アクセス許可の追加」をクリックします。

一覧に、対象APIの `access_as_user` が「委任」として追加されたことを確認します。「アプリケーションのアクセス許可」は、ユーザーとして操作する今回の方式には使用しません。
API名が同じ登録と混同しないよう、選んだAPIのアプリケーションIDが3.1で控えたIDと一致することも確認してください。

`aira-nexus` が候補に出ない場合は、同じテナントを開いているか、3.1のアプリケーションID URIとスコープが設定済みかを確認します。「自分のAPI」で見つからない場合は、「所属する組織で使用しているAPI」でも検索してください。
Microsoft公式の [スコープ公開手順](https://learn.microsoft.com/en-us/entra/identity-platform/quickstart-configure-app-expose-web-apis) では、APIとアクセス許可を追加するアプリの双方に所有者を割り当てるよう案内されています。所有者の登録状況も確認してください。
スコープが出ない場合は、3.1で `access_as_user` が追加済み・有効になっているかを確認します。
初期登録でMicrosoft Graphの `User.Read` が表示される場合がありますが、これは `access_as_user` の代わりにはなりません。現行実装はMicrosoft Graphを呼び出さないため、追加のGraph権限を要求する必要はありません。

#### 手順7：管理者同意を付与して設定結果を確認する

3.1の設定例では、`access_as_user` に同意できる主体を「管理者のみ」にしています。SPA側へアクセス許可を追加しただけでは、管理者同意は完了しません。

1. SPA用アプリの「APIのアクセス許可」で、同意対象の権限一覧を確認します。
2. 「\<テナント名\> に管理者の同意を与えます」等のボタンをクリックします。
3. 確認画面で、対象のアプリ・テナント・要求された権限を確認します。
4. 内容が意図どおりの場合に、同意を確定します。
5. `aira-nexus` の `access_as_user` の状態が、対象テナントへ付与済みであることを確認します。

管理者同意の操作は、一覧にある他の構成済み権限も対象になり得ます。意図しないGraph権限などがある場合は、そのまま同意せず、専用アプリの登録内容を確認してください。
ボタンが無効な場合は、アクセス許可が追加済みか、操作者に管理者同意を付与する権限があるかを確認します。権限がなければ、組織の手順に従って同意権限を持つ管理者が実施します。
管理者同意はAPIへのアクセス許可に対する承認であり、利用者の割り当てを省略する設定ではありません。必要なA・Bの割り当ては3.3で行います。

ここまでの設定完了条件は、以下の4点です。

| 確認項目        | 設定完了の状態                                                                          |
| --------------- | --------------------------------------------------------------------------------------- |
| アプリの区別    | API用 `aira-nexus` とSPA用アプリが別登録で、同じテナントにある                          |
| IDの控え        | API用・SPA用のクライアントIDを区別して控えている                                        |
| 認証設定        | 使用する `/auth-redirect.html` がSPAプラットフォームに登録されている                    |
| APIアクセス許可 | API用 `aira-nexus` の `access_as_user` が委任として追加され、必要な管理者同意が付与済み |

これはEntra側の登録設定の完了条件です。実SSOの成功を確認したことにはなりません。3.3の割り当てと4節のアプリ設定を行い、5節以降で実際のログイン・APIアクセスを確認してください。

### 3.3 同意・利用者割り当て・ゲスト制限

1. テナント管理者が、A・Bの利用許可と必要な同意を確認します。
2. 割り当て必須を検証する場合は、専用SPAのエンタープライズアプリで「割り当てが必要ですか？」を「はい」に設定します。
3. そのエンタープライズアプリの「ユーザーとグループ」でA・Bを割り当てます。

API側のエンタープライズアプリにも割り当て制御を設ける場合は、その設定と割り当ても確認してください。
単一テナントであっても、当該テナントのゲストは自動的に排除されません。組織内利用者だけに限定する要件は、割り当てやConditional Accessで満たす必要があります。
SSO-08用の非許可アカウントCを使う場合は、既存ユーザーの権限を外すのではなく、検証専用のアカウントを利用します。

## 4. アプリを設定して起動する

以下はリポジトリのルートで実行します。すでに `.env` がある場合はコピーで上書きせず、現在の値を確認してください。

```bash
cp .env.example .env
chmod 600 .env
```

`.env` の各項目を設定します。例中の `<…>` は説明用の置換箇所で、そのまま使用できません。

| 設定項目              | 値                                                                          |
| --------------------- | --------------------------------------------------------------------------- |
| `ENTRA_TENANT_ID`     | 対象テナントのディレクトリID                                                |
| `ENTRA_API_CLIENT_ID` | API用アプリのアプリケーションID                                             |
| `ENTRA_SPA_CLIENT_ID` | SPA用アプリのアプリケーションID                                             |
| `PUBLIC_ORIGIN`       | 選択した実行モードのオリジン。パスや末尾の `/` を付けない                   |
| `PORT`                | 開発用は `3000`                                                             |
| `BIND_HOST`           | この検証では `127.0.0.1`。未指定だと既存互換の公開待受になる                |
| `POSTGRES_PASSWORD`   | ローカルCompose用に生成したランダムなパスワード                             |
| `DATABASE_URL`        | `postgresql://aira:<URLエンコードしたパスワード>@127.0.0.1:5432/aira_nexus` |

API IDとSPA IDを逆にしないでください。`PUBLIC_ORIGIN` は、画面を開くブラウザーのオリジンと一致させます。
DBを別途用意する場合はその接続URLを使用し、以下のCompose起動を省略します。

依存パッケージを復元します。

```bash
npm ci
```

検証用DBを起動します。

```bash
docker compose up -d --wait db
```

マイグレーションを実行します。既存の検証DBを使う場合も、適用状況を確認してください。

```bash
npm run db:migrate
```

開発モードでは次を実行します。

```bash
npm run dev
```

ビルド済み画面を確認する場合は、開発サーバーを停止し、`PUBLIC_ORIGIN` を `http://localhost:3000` に変更してから実行します。

```bash
npm run build
npm start
```

`npm run dev` と `npm start` は実行中のターミナルを使用します。サーバーは起動したままにし、次節のcurlは別のターミナルで実行してください。

開発モードのViteプロキシはAPIの `127.0.0.1:3000` を参照します。`PORT` だけを変更して検証しないでください。
APIは `BIND_HOST=127.0.0.1` でループバックだけに待ち受けます。未指定だと `0.0.0.0` になるため、検証では省略しないでください。
検証用ポートを不用意に外部公開しないでください。非ループバック環境ではHTTPSが必要です。
本番相当の配信ヘッダーを確認する場合は、ビルド済み画面かHTTPS検証環境を使用します。

## 5. ログイン前の疎通確認：SSO-01

以下の `ORIGIN` を選択したモードに合わせます。HTTPS環境では `-k` で証明書検証を無効にせず、正しい証明書を用意してください。

```bash
ORIGIN=http://localhost:5173
curl -sS -i "$ORIGIN/health/live"
curl -sS -i "$ORIGIN/health/ready"
curl -sS -i "$ORIGIN/api/config"
curl -sS -i "$ORIGIN/auth-redirect.html"
curl -sS -i "$ORIGIN/api/projects"
```

| 対象                  | 期待結果                                                                                            |
| --------------------- | --------------------------------------------------------------------------------------------------- |
| `/health/live`        | 200                                                                                                 |
| `/health/ready`       | DBに接続できる場合に200。503ならSSO試験を進めずDBを確認                                             |
| `/api/config`         | 200。tenantId、apiClientId、spaClientId、scope、publicOriginの5項目が設定どおりで、DB情報を含まない |
| `/auth-redirect.html` | 200。アプリ画面ではなく空白のリダイレクト用HTML                                                     |
| `/api/projects`       | 401、`WWW-Authenticate: Bearer`、エラーコード `UNAUTHENTICATED`                                     |

Node.jsのビルド済み配信では、`/auth-redirect.html` のGET/HEADが200を返す場合だけ、`Cross-Origin-Opener-Policy: unsafe-none` になります。
通常の画面・APIやコールバックのエラー応答は `same-origin-allow-popups` のままです。CSP、`Cache-Control: no-store`、`X-Content-Type-Options: nosniff` も維持します。
これは空白ページだけの隔離例外で、APIの認証を無効にする設定ではありません。仕様の正本は [auth-popup](../.sdd/specs/auth-popup.md)です。

1. A用の分離したブラウザープロファイルで、選択したオリジンを開きます。
2. 「Microsoft Entra ID でサインイン」が表示されることを確認します。

合格条件: サインイン前には、プロジェクト一覧や非公開の3ペインが表示されないこと。
このAPIはCookie認証ではありません。後でブラウザーのログインが成功しても、Bearerを付けない上記curlは401のままです。

## 6. 実アカウントで基本SSOを確認する

サインイン前に、メイン画面の開発者ツールでNetworkを開き、「Preserve log／ログを保持」を有効にします。`/api/projects` を絞り込み、ステータスだけを観測します。
認証の要求／応答本文やヘッダー全体はコピーしないでください。観測後はNetworkログを消去し、ログのファイル出力は行いません。

### SSO-02：対話ログインとAPIアクセス

1. 「Microsoft Entra ID でサインイン」をクリックします。
2. ポップアップのアカウント選択でAを選びます。
3. 要求された認証・MFA・組織で許可された同意を完了します。

期待結果: ポップアップが閉じ、Aの表示名と3ペインが表示されます。`GET /api/projects` が200になり、認証エラーが出ません。
MSALは `prompt: select_account` を使用します。既存のEntraセッションがあれば、毎回のパスワード入力は必須ではありません。
ログイン画面から戻っただけでは合格にせず、保護されたプロジェクトAPIの200まで確認してください。

### SSO-03：プロジェクト作成・改名・永続化

1. 左ペインで試験用の名前 `SSO-A-確認用` を入力します。
2. 「プロジェクトを作成」をクリックします。
3. 中央の「選択中のプロジェクト名」を `SSO-A-改名確認` に変更します。
4. 「名前を保存」をクリックします。
5. 同じタブを再読み込みします。

期待結果: 作成のPOSTは201、改名のPATCHは200です。改名後のプロジェクトが再読み込み後も残り、選択すると中央の見出しが一致します。
既存の同名プロジェクトと混同しないよう、必要なら名称に実施回の番号を付けます。実データは投入しないでください。

### SSO-04：同じタブでのセッション復元

1. SSO-03のタブを、サインアウトせずに再読み込みします。
2. 再表示されたプロジェクトを選択します。

期待結果: 有効なMSALセッションがある場合はAの画面に戻り、一覧APIが200になります。再認証が必要な場合は、非公開データを残さずサインインを促します。
MSALの保存先は `sessionStorage` です。新しいタブやタブを閉じた後の復元を、このケースの判定に混ぜないでください。

### SSO-05：サインアウト完了と再読込

1. 「サインアウト」をクリックします。
2. Entraのポップアップで操作が必要なら、サインアウトを完了します。途中でポップアップを閉じないでください。
3. メイン画面が戻った後、同じタブを再読み込みします。

期待結果: メイン画面は `PUBLIC_ORIGIN` に戻り、サインインボタンが表示されます。Aのプロジェクトが再表示されず、ポップアップが完了後に閉じます。
非公開画面の消去だけでは、Microsoft側のセッション終了を確認したことになりません。ポップアップがサインアウトページに残った場合は未完了として調査します。

サインアウトは、発行済みアクセストークンの即時失効や、他アプリ・他端末のセッション消去を保証しません。現行APIはトークンごとのオンライン失効照会を行いません。

### SSO-06：アカウント切替とユーザー間分離

1. Aのサインアウト後、同じタブのサインイン操作からBを選択します。
2. Bの一覧に `SSO-A-改名確認` がないことを確認します。
3. Bで `SSO-B-確認用` を作成します。
4. Bのサインアウトを完了します。
5. 同じタブでAとして再サインインします。
6. Aの一覧にAのプロジェクトが残り、Bのプロジェクトがないことを確認します。
7. 別プロファイルでもA・Bをそれぞれサインインさせ、一覧が混在しないことを確認します。

期待結果: アカウント切替後の一覧と表示名が一致し、前の利用者のプロジェクトが残りません。
これは一覧と画面の分離確認です。他人のIDを指定したGET／PATCHの拒否や競合制御は、別途のAPI受入試験で確認する範囲です。

### SSO-07：ログイン中断

1. サインアウト済みの画面からサインインを開始します。
2. 認証が完了する前にポップアップを閉じます。

期待結果: 非公開ペインは表示されず、サインイン未完了を示すエラーと再試行可能なサインインボタンが表示されます。Entraセッションが有効で中断前に認証が完了した場合は、このケースを成功扱いせず未実施と記録します。

## 7. ポリシー・トークン更新・再認証を追加確認する

### SSO-08：非許可ユーザーの拒否

事前条件: 専用SPAで割り当て必須を有効にし、Cを割り当てていないこと。または組織が承認した明確な拒否ポリシーがあること。

1. C用の分離したブラウザープロファイルでサインインを試みます。
2. Entraでアクセスが拒否され、プロジェクト画面を利用できないことを確認します。

期待結果: Entra側の拒否またはサインイン未完了となり、A・Bのデータへ到達できません。Entraで拒否されるケースにAPIの403が出るとは限りません。
拒否ポリシーを設定していない場合は「対象外・理由」を記録します。外部アカウントがテナントのゲストとして登録済みなら、「別テナントだから必ず拒否される」という試験には使えません。

### SSO-09：実トークンのサイレント更新

1. 許可された試験アカウントでサインインします。
2. 初回ログイン後、メイン画面のNetworkログを消去し、フィルターを解除して測定を開始します。「ログを保持」は有効のままにします。
3. 組織で想定するトークン有効期間に合わせて、同じタブを維持します。
4. 待機後に、プロジェクト作成などのAPI操作を実行します。
5. NetworkでEntraのトークン取得通信と、その後のプロジェクトAPIの結果を確認します。

期待結果: 再認証不要な条件では、対話ポップアップを追加せずAPI操作が成功します。
トークン取得通信は `https://login.microsoftonline.com/<テナントID>/oauth2/v2.0/token` へのPOSTの200を確認します。OPTIONSや初回ログイン時の通信を、更新の証拠として数えないでください。記録するのは時刻・通信先のパス・メソッド・ステータスだけです。
サイレント更新を確認済みとするには、その試験区間でのトークン取得成功も観測してください。APIが200になっただけでは、キャッシュ済みトークンの再利用と更新を区別できません。
有効期間を一律60分とは仮定しません。観測できなければ「更新未観測」とし、OS時刻の変更、トークンの書換え、組織ポリシーの無断変更で再現しないでください。

### SSO-10：対話的な再認証が必要な場合

事前条件: 組織が承認した検証条件で、実際にサイレント取得が認証エラーになる、またはAPIが401を返すこと。テストのために既存利用者の全セッションを失効させないでください。

1. その条件になったタブで、プロジェクト操作を実行します。
2. 非公開ペインが消え、再サインインを促すエラーが表示されることを確認します。
3. 同じタブを再読み込みします。
4. 明示的にサインインし、認証・MFA等を完了します。

期待結果: 再読込だけでは失効前の非公開画面に戻らず、サインイン完了後に本人のプロジェクトを再取得します。未認証状態で作成・改名したかのような成功表示を出しません。
単なるネットワーク切断はAPIの401と同じではありません。実際の認証エラーを観測できなければ「未実施」と記録します。条件が再現しない場合、自動試験の成功を実SSOでの確認結果に置き換えないでください。

## 8. エラーを切り分ける

| 症状                                                               | 主な確認点                                             | 対処                                                                                                             |
| ------------------------------------------------------------------ | ------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------- |
| 起動できない／設定取得に失敗                                       | UUID、DB接続、`PUBLIC_ORIGIN` の一致                   | `.env` と起動モードを確認し、APIを再起動。DBの問題はreadyの結果で切り分ける                                      |
| ポップアップが開かない                                             | ポップアップ制限・拡張機能                             | 検証オリジンだけ許可し、サインインボタンを直接クリック。組織の保護機能を一括無効化しない                         |
| 認証後に白いポップアップが残り、メイン画面にサインイン未完了と出る | コールバックの200応答のCOOPヘッダー                    | 下記の確認・再試行を行う。認可コード入りのURLは共有しない                                                        |
| リダイレクト不一致／AADSTS50011                                    | SPAの登録URIと要求URI                                  | ホスト名・ポート・パスを照合し、正しいSPAプラットフォームに登録                                                  |
| コード交換でclient secretを要求／CORS関連エラー                    | 「Web」プラットフォームへ登録していないか              | SPA登録を修正。secretを追加して回避しない                                                                        |
| 管理者承認が必要／アクセス拒否                                     | 委任スコープ、同意、利用者割り当て、MFA等              | 対象APIの `access_as_user` と管理者の設定を確認。過剰なGraph権限は追加しない                                     |
| ログイン後のAPIが401                                               | APIのv2設定、audience、issuer、必須claims、期限        | API側の `api.requestedAccessTokenVersion=2` とAPI／SPA IDの取り違えを確認。IDトークンやGraphトークンで代用しない |
| APIが403                                                           | 検証済みトークンの `scp` または `azp` が不適合         | スコープが `access_as_user`、要求元が設定済みSPAであることを登録・公開設定から照合                               |
| APIが503で `IDENTITY_UNAVAILABLE`                                  | APIからの署名鍵取得                                    | Entraの署名鍵取得先へのDNS・TLS・プロキシ・通信許可を確認。鍵検証を無効化しない                                  |
| readyだけ503                                                       | DB停止・接続URL・到達性                                | DBとAPIの接続を復旧。Entra登録変更で解決しようとしない                                                           |
| ログアウト画面でポップアップが残る                                 | ログアウト先URIの登録、途中中断、Microsoft側セッション | `/auth-redirect.html` が登録済みか確認。ローカル消去だけで完了と判定しない                                       |
| ブラウザーがログイン済みでもcurlは401                              | curlにBearerがない                                     | 正常な動作。Cookieを流用したり、実トークンをシェル履歴へ貼り付けたりしない                                       |

APIの障害記録には、HTTPステータスと応答の `X-Request-ID` を使用します。Entra側では、エラーコード、発生時刻、Correlation IDを管理者と確認します。問い合わせにはクエリー文字列を含む認証URLや認証情報を添付しないでください。

白いポップアップが残る場合は、認証URLをコピーせず、そのウィンドウを閉じます。
MSAL Browser 4.30.0では、コールバックのCOOPが `same-origin-allow-popups` だと、認証元の画面からポップアップへの接続が切れる場合があります。
合成データによるChromiumの再現試験で、この挙動を確認しました。実Entraでの成功確認とは区別します。

SSH構成では、Linux側で次のようにヘッダーを確認します。認可コードやトークンは不要です。

```bash
curl --noproxy '*' -fsS -I http://127.0.0.1:18080/auth-redirect.html
```

期待結果は200と `Cross-Origin-Opener-Policy: unsafe-none` です。
古いヘッダーのままなら、アプリの所有者が現在のNode.jsプロセスを停止し、`npm run build` を実行してから、SSH手順のループバック設定を維持して起動し直します。
nginxやEntra登録の変更、暗黙的フローの有効化は不要です。
メイン画面を再読込し、新しく開いたポップアップで試してください。成功条件はポップアップが閉じ、本人のプロジェクト一覧APIが200になることです。
失敗が続く場合も、ヘッダー全体・Cookie・URLの `#` 以降やクエリーを共有せず、HTTPステータスと安全なエラーコードだけで切り分けます。
この修正はポップアップ用です。隠しiframeによる更新と実Windows/Entraの確認は、別途検証が必要です。

## 9. 合否と残課題を記録する

実際の記録はアクセス制限された検証記録へ保存します。この表は記録用のひな型であり、未記入の欄は成功を意味しません。
環境の識別名、実施日時、ブラウザー／OS、確認したコードのcommit IDを記録してください。未コミットの変更がある場合は、commit IDだけでなく試験対象の差分を識別できる管理情報も残します。

| ID     | 項目                                | 結果（成功／失敗／未実施／対象外） | 観測したHTTPステータス・証跡参照・備考 |
| ------ | ----------------------------------- | ---------------------------------- | -------------------------------------- |
| SSO-01 | 未認証・設定・DB疎通                | 未実施                             |                                        |
| SSO-02 | 実アカウントのログインとAPIアクセス | 未実施                             |                                        |
| SSO-03 | 作成・改名・永続化                  | 未実施                             |                                        |
| SSO-04 | 同じタブのセッション復元            | 未実施                             |                                        |
| SSO-05 | ログアウトと再読込                  | 未実施                             |                                        |
| SSO-06 | A・Bの切替と一覧分離                | 未実施                             |                                        |
| SSO-07 | ログイン中断                        | 未実施                             |                                        |
| SSO-08 | 非許可ユーザーの拒否                | 未実施                             | 拒否ポリシーの有無も記録               |
| SSO-09 | 実トークンのサイレント更新          | 未実施                             | API成功と更新観測を区別                |
| SSO-10 | 認証失効後の明示的再ログイン        | 未実施                             | 実際に発生した認証条件を記録           |

基本確認が成功しても、SSO-08〜SSO-10と認証実装の最終人間レビューが残る場合は、その状態を明記します。資料の作成、自動試験、モックによる応答を、実Entraでの検証完了として報告しないでください。

## 10. 試験後に片付ける

1. A・B・Cの試験ブラウザーで、開始したサインアウト処理を完了します。
2. 専用の検証環境で起動した開発サーバーまたは配信サーバーを停止します。
3. 今回起動したローカルComposeのDBだけを、不要になった場合に停止します。

```bash
docker compose stop db
```

共有DBや他の利用者のサービスを停止しないでください。検証用設定・割り当ての変更は、管理者が変更前の記録と組織の手順に従って扱います。
プロジェクト削除は基盤①にありません。確認用プロジェクトは試験データとして管理し、後片付けを理由にDBやボリュームを無断で削除しないでください。

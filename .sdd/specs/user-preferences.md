## Design
GET/PATCH /api/settings/preferences are protected by existing Entra middleware and no-store headers. PATCH accepts a strict nonempty JSON object containing language and/or theme, capped at 16KiB by the existing bounded JSON reader; invalid JSON/content type is 400 and oversize is 413. Both return the full strict preference object; malformed responses are visible failures. Database failures use the existing sanitized 500/request-ID handler, not SQL details or successful defaults.
An additive migration creates user_preferences keyed by tenant_id/object_id with enum CHECK constraints. One parameterized INSERT ON CONFLICT UPDATE applies only supplied fields; independent-field writes commute, same-field last committed write wins. No new credential handling, public-config fields or changes to the approved Copilot contract.
A shared typed schema/defaults owns runtime validation and frontend types. Existing project request-body behavior stays unchanged when its bounded reader is reused.
An explicit preferences API dependency and owner-scoped React hook load/save, validate responses, fence async results and apply acknowledged root lang/data-theme attributes before paint. Pending saves display the previous values and a saving status; user-triggered saves serialize locally. Full validated server responses alone commit, including merged fields; failed saves retain prior values with visible retry. Failed reads block editing until a retry succeeds, show ja/light plus an error, and never imply loaded defaults.
One typed Japanese-to-English catalog covers current UI text and locally generated errors, preserving request-ID suffix values verbatim and existing Japanese text when ja is selected. Project names, user names, codes and content are not translated. Changing language must not restart GitHub requests or project loads.
Settings contains preference controls and a separate GitHub section; an unconfigured/error state never hides preferences or the GitHub button. Root CSS variables supply Light/Dark to the full page and portalled modal, including focus/error colors.
Text-size compatibility: separate authenticated GET/PATCH /api/settings/text-size returns strict {size}; PATCH accepts only that nonempty field under existing16KiB/401/400/413/error rules. Migration008 creates user_text_preferences(tenant_id,object_id PK,size CHECK) independently of007 and never changes the strict old preferences response. Acknowledged owner-bound sidecar hook follows the existing epoch/owner fence and serial-save/retry contract.
Migration010 atomically replaces only user_text_preferences_size_check to allow extra-small alongside the existing three values. It changes no stored row, key, default, ownership or language/theme setting; migration008 remains byte-for-byte unchanged. Apply010 before publishing the fourth option. A missing010 write must expose the existing sanitized error and retain the acknowledged size, never substitute a successful default.
Typography uses a root data-text-size attribute and font-only theme tokens/body font, not root rem-size, CSS zoom, transform or PDF renderer zoom; inherited portals share tokens and existing spacing stays fixed. All existing text classes must be audited for hardcoded font sizes. No document image/embedded SVG text is rewritten.

## Assumptions / risks
Confirmed: server-side per-user persistence and whole-UI translation; user content is unchanged. Defaults are Japanese/Light until a successful read, not OS/browser detection; a first-load default-to-saved transition is possible. Signed-out UI resets to defaults; no preference data is browser-persisted. Existing GitHub setup/credential policy and future chat scope remain unchanged; disabled reasons are translated. Live database migration requires separate operator consent; no rollback/data deletion or role/RLS changes are in scope. Cross-tab changes reload on remount rather than push synchronization; PATCH returns the current merged row. Browser/SQL spikes, real assertion Red/Green, static checks and independent risk reviews are required before completion.
Isolated CSS feasibility on the unchanged Root synthetic UI passed1→.9→.8→1 for427 text nodes, including11 actual settings-portal nodes, with root rem/header/grid tracks and synthetic image/canvas geometry unchanged. The probe waits for computed target sizes because existing buttons animate font-size transitions; its initial header-only locator and one-frame timing attempts failed and were corrected without weakening target assertions. Evidence: .playwright-mcp/pane-font-feasibility.js and .json. This is not a text-size API/native implementation test or actual PDF/user-file verification.

Extra-small spike (2026-11-16): user confirmed70%; disposable PostgreSQL atomically widened the existing CHECK, preserved all three old records, accepted extra-small and still rejected unknown sizes.

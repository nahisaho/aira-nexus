## Design
Migration012 adds `purge_pending boolean NOT NULL DEFAULT false`, constrained to ready+trashed files. Existing immutable bytes/hash/ETag and quota rules remain unchanged until explicit purge completion; this feature replaces the original no-purge limitation, not ordinary reversible deletion.
`DELETE /api/projects/:id/files/trash` uses existing authentication/project middleware and FileService.emptyTrash. Existing list and content routes remain unchanged; no client-supplied object key/file set is accepted.
Repository admission marks current ready trash under the existing owned-project transaction/row lock. Select pending files in bounded100-row batches, perform private ETag-conditional Azure Blob removal outside DB transactions, then owner-lock and delete only that pending metadata row. New trash after admission is not marked by that request; concurrent owner-confirmed purge requests may coalesce pending work.
Keep pending rows in trash listings/usage until completion; forbid restore with409 and localized retry guidance. Pending is monotonic: application paths never clear it, only remove the metadata after confirmed absence. A crash after blob removal but before DB deletion leaves a durable retry record; a concurrent finisher's already-deleted metadata is harmless. Concurrent requests may both attempt conditional removal and then cleanup; never skip in-flight rows or return204 until a pending batch query is empty. No automatic purge worker or silent retry is introduced.
Bound each request to5 minutes with AbortSignal.timeout/any plus the caller's signal. Check abort before admission, per batch/file and after Blob removal; preserve pending metadata on ambiguity. Storage failure returns503 with partial-deletion guidance, never204.
Azure remove checks private-container policy and stored ETag, which is non-null under the existing ready-state DB constraint. Object keys use immutable per-upload UUIDs, never reused or overwritten. A successful conditional delete or404/already-absent result is idempotent success; Azurite may return412 for an If-Match deletion of an absent blob, so accept that case only after a post-attempt existence check confirms absence. A present wrong-ETag blob must never be removed or accepted.
UI uses Radix AlertDialog, existing write/list fencing and a FilesApi.emptyTrash method. Confirmation closes on request start, disables conflicting controls and displays deletion status; reload after both success and partial error reconciles quota/rows. No automatic live empty-trash request is authorized.
Policy: active/uploading/failed→unchanged; trash+restore-before-admission→active/retained; trash+admission→pending; pending+restore→409; pending+trash→idempotent; pending+blob-error/abort→pending+charged; pending+confirmed-absence+DB-delete→gone+quota-released; gone+retry→success.
## PASS conditions and counterexamples
`REQ-FTP-001`: cancel makes zero API calls; confirm makes one; only trash has Empty trash; empty/busy controls disabled; ordinary upload/reload and localization preserved; stale scope completion cannot clear a new project's rows. Counterexample: confirm-free request, upload in trash, false success, stale callback.
`REQ-FTP-002`: actual PostgreSQL/Azurite removes originals across more than100 rows, keeps active/foreign data and releases exact usage; verify malformed IDs and both identity dimensions before touching Blob storage. Counterexample: delete active/foreign objects or remove metadata before Blob confirmation.
`REQ-FTP-003`: injected storage failure, wrong ETag, metadata failure after Blob deletion, abort, service recreation and concurrent repeats preserve/recover the policy table; assert pending bytes remain in usage/quota admission and exercise explicit restore race controls. Counterexample: restore a missing original, free quota on partial failure, swallow wrong ETag or re-delete a new active file.

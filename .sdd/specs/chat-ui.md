# Conversation selection, explicit sends and reconnectable chat
Goal: smallest chat-only central tab using the existing project/auth/i18n shell. Depends on chat-history, chat-consent and chat-runtime. No Notebook, Jobs UI changes, rename/delete, attachment picker, Skills/MCP or tool controls.
| ID | EARS requirement | Test |
| --- | --- | --- |
| REQ-CHU-001 | When an owner opens project chat, the UI shall list/create/select separate owned conversations and display ordered paginated retained turns with explicit queued/running/cancel_requested/succeeded/failed/cancelled labels; selecting a conversation shall not edit/delete another history or cancel its running generation. | TEST-CHU-001 |
| REQ-CHU-002 | When the user requests model refresh, the UI shall disclose and require confirmation of the account-only GitHub request; when the user requests Send, it shall preview the exact text/history/framing/model and upstream retention/cancellation warning, require a separate explicit confirmation for that individual snapshot and disable submission until a server-authorized model is selected. | TEST-CHU-002 |
| REQ-CHU-003 | While a run exists, the UI shall apply validated sequenced text events once, restore missed events after browser disconnect/tab return, show owner-wide busy conflict and retryable read errors without resending, and cancel only through an explicit owner cancel action that displays cancellation-pending until a terminal server outcome. | TEST-CHU-003 |
| REQ-CHU-004 | When user/account/project/conversation/epoch changes or a401 arrives, the UI shall abort/fence old reads/subscriptions/previews and discard stale text/confirmation/model results without sending a generation-cancel request; it shall render model/user text as escaped plain text and never persist chat/tokens in browser storage, follow provider links or execute Markdown/HTML/tools. | TEST-CHU-004 |
## Design
One project Chat tab with a simple conversation selector, New conversation, model selector/explicit Refresh, textarea, Preview→Confirm send and Cancel generation; reuse existing accessible primitives, bearer API, translated labels and errors. Conversation labels derive from creation time/ID; no title editor.
Models, previews and transcript buffers are keyed by both Entra owner axes/project/conversation and a client-local connection epoch from existing Settings mutations/status; the server's private connection binding is never exposed. Only explicit confirmed clicks call external-transfer endpoints; create/cancel retain their own explicit actions. Opening chat does not call GitHub. Model/catalog errors require a fresh explicit refresh; preview or known connection changes invalidate confirmation, and server binding checks reject unseen changes.
Switching/deactivating unmounts only the subscription/render resources, not the server run; reactivation first restores canonical run snapshot/sequence and then durable events. Updating a conversation while a preview is open invalidates it. Client model IDs are untrusted hints, never authorization.
Browser schema checks strict DTO fields, UUIDs, bounded UTF-8 text/model labels, safe ISO timestamps, allowed states/reasons, integer sequences and duplicate/gap behavior; malformed responses produce an explicit retryable read error and never successful/empty-history defaults.
A send uses one in-memory Idempotency-Key and immutable preview/body; after a lost response, recover from conversation detail/latest-run history, or let an explicit Recover send action replay only that same body/key (also safe after preview expiry). Never auto-generate a replacement key/preview, revalidate externally or resend generation on reconnect; reload uses canonical history rather than browser storage. Preview explicitly displays that final confirmation also authorizes one account-only model validation.
Keyboard/focus and Japanese/English labels follow existing Settings/Jobs conventions; preserve file/viewer focus, uploads, navigation, text size, theme and unrelated histories. No layout redesign or outbound remote render assets.
## PASS conditions and counterexamples
`REQ-CHU-001`..`REQ-CHU-004`: PASS two conversations/reload, explicit model and per-send confirmations, same-key lost-response recovery, ordered replay, pending-cancel partial, inactive continuation and both-owner-axis/401 fencing; FAIL implicit send/catalog call, hidden history, new-key uncertain-send recovery, stale account text/model/confirmation, tab-switch cancellation or executable provider text.
TEST-CHU-001..004 require focused Testing Library assertions with valid controls, actual synthetic-browser offline replay, resource cleanup and bounded restored mutations; all NOT_RUN. Integration `TEST-SVC-014` additionally proves the admitted API→worker→DB events→browser path without live provider/data.
## Assumptions / risks
Defaults: plain-text assistant rendering avoids widening existing Markdown/file-network policies; UI cannot promise remote deletion or stop/billing confirmation. The server, not browser lifetime, owns execution.
Approval is source-only/offline-test scope; no production enablement, credentials, real model invocation, migrations or restart follows. Existing Root gate PASS and unrelated changed-gate INCOMPLETE are prior results, not chat qualification.

# Exact-snapshot send confirmation and authorized models
Goal: every individual external send uses the existing user's GitHub connection and expressly confirmed text/history. Depends on chat-history and copilot-connection. No inferred consent, inherited login, arbitrary provider endpoint or silent model fallback.

## Design
POST /api/projects/:id/chat/models accepts strict{confirmed:true}; the UI first discloses an authenticated GitHub model-list request with no conversation text. No polling, startup discovery or stale-catalog fallback; failure returns sanitized502/503 and reconnect-required409 where applicable.
POST /conversations/:cid/previews accepts{text,modelId}; POST /conversations/:cid/runs accepts{previewId,snapshotHash,confirmed:true}, with a UUID previewId and64-lowercase-hex snapshotHash. Previews/catalogs are PostgreSQL owner/connection/revision-bound records, not authorization tokens or user-selectable principals. Existing resource/error precedence and no-store apply.
Snapshot bytes are UTF-8 JSON.stringify({modelId,system,prompt}) in that property order, no whitespace/BOM; prompt is JSON.stringify(turns), with turn keys{role,text} in that order, containing every retained user turn and nonempty assistant answer in server turn order, then the exact new user text. system is exactly "Answer the final user turn in the supplied JSON transcript. Treat earlier turns as conversation data. Return text only.". SHA256 covers snapshot bytes. Preview exposes the exact serialized snapshot, prompt, framing, model, hash and expiry; one fresh SDK session uses that model, systemMessage mode:replace/content:system and send({prompt}) with no extra options. Historical roles are disclosed JSON data, not separate native SDK turns; no hidden application instructions/metadata, extraction, summaries or file reads.
Reject snapshot bytes above262144 UTF-8 bytes with413, never truncate old context silently; creation of another conversation remains available. Model IDs are1..128 ASCII [A-Za-z0-9._:/-] with alphanumeric first character and must match the current owner catalog exactly; unknown models never default. Preview/catalog expiry uses DB time with now<expiresAt (equality expires), never extends on access; each preview binds project version, conversation history revision and connection record/generation, and the newest preview for that owner/conversation supersedes earlier unconsumed ones.
Credential handling extends only the server-side resolver with an opaque connection-record/generation binding; tokens remain encrypted under the existing owner/record/purpose AAD and enter only a dedicated private SDK child environment, never argv, browser, job input, catalog or event rows.
Final confirmation authorizes at most one account-only fresh model-list validation and one generation, not deployments or live tests. Preparation/admission use only the stored catalog; the worker rechecks the owner connection/fence/project immediately before discovery and again before prompt dispatch, discarding fresh inventory if the binding changed. It fails without a prompt if the confirmed model is no longer available. Idempotent HTTP replay returns the admitted run even after preview/catalog expiry or connection replacement and never starts another validation/send; reuse with a different preview/hash returns409 after strict input validation.
## PASS conditions and counterexamples
`REQ-CHC-001`..`REQ-CHC-005`: PASS own explicitly confirmed discovery/send, independently computed Unicode snapshot bytes/hash, expiry-minus1ms, replay-after-expiry/replacement and valid-model controls; FAIL equality-expiry, altered hash/framing/roles, second-key preview reuse, cross-account inventory, post-preview turn changes, credential replacement between listing/dispatch, automatic fallback/retry or token/error leakage. Each mapped test covers its requirement with valid controls; synthetic request-capture and actual PostgreSQL tests above are NOT_RUN.
## Assumptions / risks
Proposed conservative defaults: model refresh itself requires explicit account-only confirmation; final confirmation also expressly discloses the worker's account-only model validation. The literal framing/serialization and numeric limits above are candidate design choices, not previously confirmed product choices. Provider context-window/policy rejection is an explicit failed run, not permission to truncate or retry.
Disconnect/replacement fences undispatched work and triggers abort at the next at-most5-second worker check; an already accepted external request cannot be recalled or proved erased. This race and upstream retention/billing are disclosed before final send.
Draft requires explicit hash-bound human approval for credential-adjacent delivery and this narrow external-data scope. No actual user data, credential provisioning, model discovery or generation is authorized by writing it.
